# 2026-08-17

## Paste into chrome inputs was silently suppressed

**Reported as:** the Settings → Google OAuth Client ID field accepts typing but
ignores paste.

**Actual scope:** every text input in the app — the board name, the find bar,
the command palette, the Settings client ID and the style panel's custom colour
field.

### Cause

`src/app/app.ts` installs a native `paste` listener on `window`. It has to be on
`window` and it has to be a native event: pasted *image* data is only reachable
through `ClipboardEvent.clipboardData`, and a canvas has nothing focusable to
bind a listener to. Clipboard events bubble, so that listener also received
pastes aimed at `<input>` elements in the chrome, and it called
`event.preventDefault()` unconditionally — cancelling the browser's own text
insertion — then ran `actions.paste()`, dropping a stray copy of the board
clipboard onto the canvas as well.

`installKeyboardShortcuts` had already solved the same problem for keystrokes
with a module-local `isTypingTarget` guard. The clipboard listener predated
nothing and postdated nothing in particular; it was simply written in a
different file and never picked the guard up.

### Fix

- `src/input/keyboard.ts` — `isTypingTarget` is now exported, with a comment
  explaining why it is shared rather than duplicated.
- `src/app/app.ts` — the paste handler returns early for typing targets. The
  existing `textEditor.isEditing` check is kept: it still covers the case where
  the canvas text overlay is open but focus sits elsewhere.
- `docs/05-interactions.md` — the Clipboard section now states that pastes
  bubbling out of chrome fields are left to the browser, and why.
- `test/e2e/board.spec.ts` — a `pasting into chrome inputs` describe with two
  tests: text lands in the Settings field, and a paste into the find bar does
  not add an element to the board.
- `LEARNINGS.md` — the general rule: any `window` listener for a bubbling event
  must ask whether the user is typing.

### Verification

`npm run typecheck`, `npm run build`, `npm test` (278 passing) and
`npm run test:e2e` (77 passing) all clean. Both new e2e tests were confirmed
failing against the pre-fix build first.

### Note for later — superseded, and it was wrong

## Drag and drop: the browser was navigating away from the app

Follow-up to the above, and a **correction to what the previous section
originally claimed**. The note left under "Note for later" said the `drop`
listener was on `window` and would load a board behind an open dialog. Both
halves were wrong. The listeners were on `this.canvas`, and the real failure ran
the other way.

### Cause

`dragover`/`drop` were bound to the canvas only. A file dropped anywhere else on
the page — the top bar, the tool rail, the style panel, an open dialog — reached
no handler at all, so the browser's default action ran, and that default is to
**navigate to the dropped file**. The app is replaced by a rendering of the JSON
or the image; a dirty board gets only the generic `beforeunload` prompt, and a
clean one goes without a word. A drop that missed the board by a few pixels was
indistinguishable from a crash.

Binding to the canvas looks like the cautious choice, which is what makes this
worth remembering. Suppression and handling need different scopes: suppress
page-wide, handle where it makes sense.

### Fix

- `src/app/app.ts` — both listeners moved to `window`. `dragover` must be
  prevented too or no `drop` fires at all. File drags are detected with
  `dataTransfer.types.includes('Files')`, which is readable during `dragover`
  where `files` is deliberately empty; drags without files fall through
  untouched so text can still be dragged into the board-name field.
- Placement: `event.target === this.canvas` keeps the old drop-at-cursor
  behaviour; anywhere else falls back to `viewportCenter()`, matching what
  pasting an image already does. Board files ignore the point.
- `src/ui/dialogs.ts` — new exported `isModalDialogOpen()`. A drop over a modal
  is claimed (so the browser cannot navigate) and then discarded.
- `docs/05-interactions.md` — the Drag and drop section now specifies all four
  behaviours and the reason for the window-level binding.
- `test/e2e/board.spec.ts` — a `dropping files` describe, six tests.
- `LEARNINGS.md` — the two listener-scope failures, recorded as a pair.

### Verification

`npm run typecheck`, `npm run build`, `npm test` (278) and `npm run test:e2e`
(83) all pass. Three of the six new tests were confirmed failing pre-fix; the
fourth (non-file drags) passed already and is a regression guard, as is the
canvas drop-at-cursor test, which covers a path that had no test before and that
this change rewrote.

### What a synthetic event cannot prove

The navigation itself is untestable from Playwright — an untrusted, dispatched
`DragEvent` has no default action to observe. The tests assert
`event.defaultPrevented` instead, i.e. that the app claimed the drop. That is
the decision under our control; the navigation is the documented browser
behaviour it protects against.
