# 2026-11-10 — Workspaces within a file: UI ideas and a plan

Branch `claude/confident-newton-gro5wn`, on top of bd0e3d8. **Planning only.
No source, format or docs change.** Only `PROMPT.md` and this file changed.

## The ask

Several independent "workspaces" inside one board file. A file starts with a
default workspace, a new one is an empty environment, and going back to an old
one restores its work. The user wanted visual UI ideas first, then a plan
artifact.

## What was made

- **UI ideas (design canvas):** https://claude.ai/artifact/PtiE9Nhxhso9Tj1TVn1ZUH
  Four directions, each at desktop and phone size, drawn over the real top bar
  and tool palette (cut from the built `index.html` with Playwright):
  A tab strip, B top-bar switcher, C thumbnail panel, D floating pill.
- **The plan:** https://claude.ai/artifact/P8buPB26C7zEYfobqYDVCu

Both are private claude.ai artifacts, so they are not in the repo.

## Decisions the user made

- **Switcher: B**, a button beside the board name that opens a list styled like
  the recent-boards menu.
- **Undo: per workspace.** Undo only changes the workspace on screen.
- **Phone top bar: icon-only switcher below 760px** (answered in a comment on
  the plan). The board name keeps its place. The text button that takes the
  board name's place, as drawn in the phone mockup, is left for when the phone
  bar is reworked.

## What the plan proposes (not yet agreed)

- **Format 2.0.0.** `workspaces[]` of `{id, name, canvas, viewport, elements,
  meta}` plus `activeWorkspaceId` replace the top-level `canvas`, `viewport`
  and `elements`. `files` and `meta` stay board-level. Migration from 1.6.3
  wraps the drawing into one workspace with the fixed id `ws_1`.
  - Major, by the changelog's own rule: within a major version a newer file
    never uses anything an older reader lacks a rule for. A 1.6 build writes
    back only the top-level fields it knows, so it would drop extra workspaces.
  - Rejected: top level as the first workspace plus a list (1.7.0, lopsided and
    silently lossy in old builds), and a flat element list with `workspaceId`
    (old readers would draw every workspace on top of the others).
- **Store: one workspace on stage, the rest parked.** `state.document` stays
  the flat shape every drawing module reads, so the renderer, hit-testing,
  commands and exporters do not change. `store.history` becomes a getter for
  the staged workspace's history. `documentForSave()` becomes `boardForSave()`.
- **Switching is not an edit** (like a pan). Add, rename, move, duplicate and
  delete are edits but are on no undo stack. Delete asks when there is content.
- **Background and grid per workspace.** A new workspace copies the current
  one's.
- **Four phases:** format read/write, store operations, the switcher, then
  reach (PDF of all workspaces, find across workspaces).

## Found while reading the code (must be handled in phase 1)

- `Autosave.write` deletes a board's copy when
  `document.elements.length + preserved.length === 0`, and `app.ts:519` uses
  the same count before asking about unsaved work. With workspaces both must
  count every workspace, or a board whose active workspace is empty (right
  after "New workspace") loses its recovery copy.
- `validateDocument` reports unreferenced `files` from one element list. It
  must count references board-wide.
- `ImageCache.prune` is only a bitmap cache, so pruning by the staged elements
  costs a re-decode, not data.
- A 1.6 build opening a 2.0.0 file warns, finds no top-level `elements` and
  shows an empty board. Shipped builds cannot be changed.

# Building it: format 2.0.0, the store, the switcher

The user said "Ok, work on the plan." Phases 1–3 are built. Phase 4 (PDF of
every workspace, workspace name in export file names, find across workspaces,
a workspace count in the recent menu) is not started.

## Decisions taken without asking (the plan's recommendations)

- **Duplicate workspace is in** (question 2).
- **Unknown fields are kept** (question 3): top-level AND workspace-level, not
  only top-level. A workspace object can gain fields in a minor version just as
  the board can. The 2.0.0 schema sets `additionalProperties: true` at those
  two levels only, since a 2.0 writer round-tripping a 2.1 file writes the
  2.1 fields under `schemaVersion: 2.0.0`.
- **Page Up / Page Down** switch workspaces (question 4). Unmodified only:
  Ctrl+Page Up/Down is the browser's tab switch.
- **PDF of every workspace waits for phase 4** (question 5).

## What changed

- **Format** (`types.ts`, `document.ts`, `migrate.ts`, `workspaces.ts`):
  - `Workspace` and `MindflowBoard` are the file shape. `MindflowDocument`
    stays as the in-memory "board seen through one workspace"; `$schema` was
    dropped from it.
  - `LoadResult extends StagedBoard`: the active workspace on stage, the others
    parked, plus `warnings` and `sourceVersion`.
  - `serializeBoard(board)` writes every workspace; `serializeDocument` is a
    one-workspace convenience.
  - Migration 1.6.3 → 2.0.0 wraps the drawing into `ws_1` "Workspace 1".
  - The 2.x file in the 1.x shape is read as one workspace (info note). Both
    shapes at once: the top-level drawing becomes a last workspace (warning).
  - Element ids unique board-wide: a later workspace's duplicates are
    reassigned and its bindings and frame references follow
    (`remapElementIds`).
  - `$schema` is always written as the current URL. Before, a 1.x file kept
    its old `$schema` on save, which was a latent bug.
  - Validation per workspace; image use counted board-wide.
  - `isNewerMajor`: a file from a later major opens detached (origin `new`)
    with a toast.
- **Schema** `docs/schema/mindflow-2.0.0.schema.json`, generated from 1.6.3;
  the element `$defs` are byte-identical.
- **Example** `docs/schema/examples/workspaces.mindflow.json`, two workspaces
  sharing one image, generated through `serializeBoard`.
- **Store**: `workspaces`, `activeWorkspaceId` in `AppState`; one `History` per
  workspace behind a `history` getter; `switchWorkspace`, `addWorkspace`,
  `duplicateWorkspace`, `renameWorkspace`, `moveWorkspace`, `deleteWorkspace`,
  `workspaceSummaries`, `boardForSave`; new change reason `workspace`.
  - Switching bumps `settled` (so an old dirty checkpoint is refused) but not
    `revision` (so a save in flight lands clean).
- **Save paths**: `saveToFile(board)`, Drive `saveBoard(board)`, autosave
  `BoardSnapshot { board, unsaved }`, `countElements` reads both shapes.
- **App**: `leaveStage` (commit editors, `controller.cancelGesture()`, close
  popover) before every change of stage; `deleteWorkspace` asks when there is
  content (`describeDeletion`).
- **Controller**: public `cancelGesture()` and an `abandoned` pointer set whose
  moves and release are ignored.
- **UI**: `src/ui/workspaceMenu.ts` (list, inline rename, a row menu inside the
  popover); `Popover` got `onEscape`; the toolbar's `buildWorkspaceButton`;
  five icons (`workspaces`, `chevronRight`, `chevronDown`, `more`, `plus`).
- **Palette**: a Workspaces group, including *Go to workspace: name* per row.

## Beyond the plan: the phone top bar

At 390px the bar's groups overlap; on HEAD seven buttons could not be tapped
(measured with `elementFromPoint` at each centre). The new switcher was the
eighth. Making the first group rigid moved the overlap onto Save. So below
760px the bar now scrolls sideways, like the tool palette, and every group
keeps its width. Above 760px a named switcher does not fit until about 784px,
so its compact (icon-only) form starts at 860px. This is a layout change on
phones that the user did not ask for. It is in the summary. The queued
"Fix top bar overlap on narrow screens" task is now mostly moot: everything is
reachable, though a phone still has to swipe the bar to reach Settings.
