# 2026-08-15 — Initial build

Greenfield. Built MindFlow end to end: a static, serverless digital whiteboard
with a fully documented save format.

## What was built

**Application** (`src/`, ~7,500 lines TypeScript)

- `model/` — types, element registry, geometry, document load/validate/serialise,
  migration harness
- `store/` — observable store, command system, undo/redo
- `render/` — Canvas 2D renderer with viewport culling, selection overlay, image
  decode cache, PNG + SVG export
- `input/` — gesture state machine, hit-testing, snapping, connector binding,
  transform maths, keyboard shortcuts
- `ui/` — toolbar, contextual style panel, in-place text editor, dialogs, toasts
- `io/` — File System Access with download fallback, IndexedDB autosave, image
  import, Google Drive
- `app/` — application shell and the actions layer

**Contract** (`docs/`) — nine numbered documents, a JSON Schema (draft 2020-12),
three example boards, and a schema changelog.

**Tests** — 183 unit/contract (Vitest) + 23 end-to-end (Playwright). All passing.

## Decisions made with the user

| Question | Choice |
|---|---|
| V1 scope | Standard whiteboard (core + sticky, images, grouping, snapping, bound connectors, export) |
| Build | Single self-contained `index.html` via esbuild |

| Drive | Auto-created folder, `drive.file` scope only |

## Non-obvious things worth remembering

**`file://` blocks ES modules.** This is the reason for the whole single-file
build — browsers fetch module scripts with CORS semantics and a local page has an
opaque origin. Shipping a module script would break double-click-to-run.

**OAuth cannot work from `file://`** (origin is `null`). Drive is HTTP(S)-only.
Documented as a boundary, not worked around.

**The element registry is the keystone.** No code outside `render/shapes/` branches
on `element.type`. That makes new types cheap *and* makes the registry
runtime-inspectable, which is what lets `contract.test.ts` verify that code and
schema agree — TypeScript types vanish at runtime and cannot be checked that way.

**Commands record `before`/`after` for only the elements they touch**, so undo is
correct by construction rather than hand-written per operation, and history stays
small even with embedded images.

## Bugs found and fixed during browser testing

1. **`pointerup` position was being discarded.** Gestures committed using the last
   `pointermove`, losing the final few pixels. For a fast marquee drag this lost
   almost the entire gesture — the marquee selected nothing. Fixed by re-running
   the gesture update with the release position before committing. Affected shape
   creation, connector creation, marquee, move, resize and rotate.

2. **Two apparent bugs that were correct behaviour**, both caught while writing
   tests and worth not "fixing" later:
   - Unfilled shapes are hollow to clicks by design (click-through).
   - Resize handles take priority over moving, so a freshly-created (and therefore
     selected) shape cannot be grabbed on its outline.

3. **Autosave does not work from `file://`** — browsers block IndexedDB on opaque
   origins. Found during the final visual check, when the app surfaced its own
   "autosave unavailable" warning. The graceful degradation worked exactly as
   designed, but the docs had claimed autosave unconditionally; corrected in
   `docs/06-persistence.md`, `README.md` and `LEARNINGS.md`. Explicit `Cmd+S`
   saving is unaffected.

# 2026-08-15 (later) — Two bug fixes

Both reported from real use after the initial build.

## 1. Text looked wrong while editing, normal once committed

**Root cause.** The canvas and the `<textarea>` place a first baseline by
different rules, and sharing a font stack does nothing about it:

| | First baseline from the top of the line box |
|---|---|
| Canvas / `docs/07-rendering.md` | `fontSize × 0.8` |
| CSS | `half-leading + ascent` = `(lineHeightPx − (ascent + descent)) / 2 + ascent` |

Measured in Chrome for the default 20px sans: **16px vs 20px**. The DOM text sat
4px — a fifth of an em — below where the canvas draws it, which on a tight
`text` element reads as the glyphs being clipped by their own editor outline.

The `docs/07-rendering.md` rationale for the fixed `0.8em` was *itself* wrong: it
claimed the fixed offset is what keeps the two engines in agreement. It never
did. Corrected, and turned into an explicit note for anyone overlaying HTML.

**Fix** (`src/ui/textEditor.ts`). Measure the CSS baseline for the typography in
use — a zero-height `inline-block` at `vertical-align: baseline`, cached per
typography — and fold the difference into the `padding-top` that already
emulates vertical alignment. Where padding cannot express it (top-aligned text
with zero padding, since the correction is upward and padding cannot go
negative), the remainder becomes a `translateY` appended **after** `scale()`, so
it reads in scene units and rotates with the element.

Deliberately kept `0.8em` as the published contract rather than moving the canvas
onto font metrics: the format's promise is that a board renders without running
MindFlow, and a font-independent constant is what makes vertical placement
specifiable. The editor is the app-internal side, so the editor is what corrects.

Also folded out the duplicated literal `0.8` — now `BASELINE_RATIO` in
`render/shapes/shared.ts`, shared by the canvas, the SVG export and the editor —
and fixed a latent mismatch where the editor wrapped an `autoWidth` text element
for measurement while the canvas does not.

## 2. A locked element could never be unlocked

**Root cause.** Three individually defensible decisions composed into a one-way
door: `elementAt`/`elementsInBox`/`selectAll` skip locked elements so a locked
background behaves like scenery, and `toggleLock` clears the selection on
locking. Nothing could then reach the Unlock button, which only appears for a
selection.

**Fix.** Right-click falls back to a locked hit when nothing unlocked is under
the pointer — ordinary clicks are untouched, so the scenery behaviour survives.
A locked element that is selected this way draws a dashed, handle-less frame; the
style panel collapses to a single Unlock button; and gestures, `deleteSelection`
and `nudge` all filter on `locked`, since the selection is no longer guaranteed
editable. `canTransform` in `render/overlay.ts` is the shared predicate.

Locking now also emits a toast naming the way back, which is the only thing on
screen that could teach it.

## Tests

- `test/unit/locking.test.ts` — 8 new: click-through, marquee, opt-in pick,

- `test/e2e/board.spec.ts` — 3 locking, 3 baseline, 1 commit-geometry.

The baseline tests derive the two sides independently (the published formula

## Gotcha worth keeping

An **unfilled rectangle is a useless fixture for a click-through test** — it is
click-through already, so the test passes without proving anything. The first
draft of the lock tests did exactly this. Use a sticky.

A second gotcha, found by a flake in the new tests: `TextEditor.open` focuses
inside a `requestAnimationFrame`, so a test that clicks and types immediately
loses the leading keystrokes to the canvas — where letters are tool shortcuts.
`'Baseline'` arrived as `'eline'` *and* changed the active tool on the way. Tests
now wait for `.mf-text-editor` to be focused first. Not a user-facing issue at
human typing speeds.
