# 2026-10-29 — Investigation: "the sidebar sometimes gets hidden" (iPad)

Branch `claude/ipad-hidden-chrome-investigation`, on top of 55fd98d.
**Investigation only, no code changed.** The user asked not to start the fix.

## The ask

"sometimes the sidebar gets hidden because of some bug, investigate but dont
start work on it", with an iPad Safari screenshot (1640 × 2360, so 820 CSS px
wide at @2x). It shows the board and nothing else: no top bar, no tool
palette, no style panel.

## Finding: the page is pinch-zoomed, the chrome is just off-screen

Evidence from the screenshot pixels:

- **Everything under Safari's tab bar is pure `#ffffff`, edge to edge.** If the
  document or `.mf-canvas-wrap` had scrolled, the uncovered strip would show
  the body background `--mf-bg: #f6f7f9`. It shows nowhere, so the visible area
  is entirely canvas.
- **The canvas is upscaled about 4x and Safari's own UI is not.** Safari's tab
  text is crisp at 1 px anti-aliasing. On the board, a stroke carrying under
  1 device px of ink is smeared over about 5 px, and the embedded image shows
  smoothed blocks 4 to 5 device px across. A canvas at DPR 2 drawn 1:1 spreads
  such a line over at most 2 px. This is the bilinear upscale a page zoom
  (visual viewport `scale` > 1) applies to a canvas bitmap.
- Reproduced in Chromium (scratch script, not committed): built `index.html` at
  820 × 1050 @2x, `Emulation.setPageScaleFactor(4)`. `.mf-tools` leaves the
  visual viewport. A 2 px grid line goes from crisp to an 11 px smear, while
  the top bar's DOM text stays crisp. Same signature as the user's screenshot.

## Why it sticks

At 4x the visible area is about 205 × 260 CSS px, inside the canvas. A finger
pinch there is the canvas's own pinch (`touch-action: none`, `input/pinch.ts`),
so it zooms the **board** and never the page. The repro confirmed it: board
zoom 1.05 → 5.24, `visualViewport.scale` still 4. Even if part of the chrome
were visible, `blockPageZoom` cancels every `gesture*` event on the page, so
a pinch there could not zoom the page back **out** either. Nothing on screen
undoes it. Reloading does (the board is recovered from autosave), and so
should a trackpad pinch-close.

## Most likely trigger: a trackpad pinch (iPad keyboard)

The three page-zoom layers from PR #7 (`input/pageZoom.ts`, LEARNINGS
"`user-scalable=no` does not stop the page zooming on a touchscreen") all
target **touch** input:

1. The viewport meta: iOS ignores it for user zoom.
2. `touch-action: pan-x pan-y`: applies to touch input only.
3. Cancelling `gesturestart/change/end`: on iOS these come from touch
   handling. *Inferred, not verified:* a trackpad pinch on iPadOS reaches
   WKWebView's own scroll-view zoom, with no touches and probably no gesture
   events.

WebKit's Simon Fraser (bugs.webkit.org 230545, 2021) says iOS dispatches
`wheel` events only for the Magic Keyboard trackpad, "and there you have a
trackpad which supports pinch-zoom already", meaning native page zoom, not
`ctrlKey` wheels. So `controller.onWheel`'s Ctrl/Meta zoom path never fires for
it either. Miro and Figma users report the same thing on iPad Safari: a
trackpad pinch zooms the entire page, sidebars included.

Circumstantial: the screenshot has iPadOS's window-resize grabber in the
bottom-right corner (windowed apps), a setup common with a keyboard and
trackpad. The device sizes that fit (iPad 10th gen / A16, iPad Air 11") all
have trackpad keyboards. **Still to confirm with the user: was a trackpad in
use when it happened?**

The `pageZoom.ts` header says an iPad driven by a trackpad "is still covered",
but that only shows `maxTouchPoints > 0` is true there. It does not show that
a trackpad pinch sends the events being cancelled.

## Considered and less likely

- **Focus zoom on a small-font field** (frame name editor 13 px, hex input,
  find bar). `maximum-scale=1` caps it on iPhone, and iPad Safari in desktop
  mode is not known to focus-zoom. `TextEditor.focusEditor` calls `focus()`
  without `preventScroll` (unlike `FrameNameEditor`), but that can only scroll
  `.mf-canvas-wrap`, which would leave the top bar in place and show a grey
  strip. Neither appears.
- **Soft-keyboard viewport offset not restored.** That shifts the page without
  scaling it, so there would be no upscale blur. Ruled out by the pixels.
- **Canvas bitmap smaller than its box** (stale `renderer.resize`). This would
  blur the canvas but cannot hide DOM chrome. Ruled out.

## Fix directions (not started)

- **Detect.** Nothing in `src/` reads `visualViewport`. A `visualViewport`
  `resize` listener can see `scale > 1`.
- **Recover.** iOS has no API to set the page scale. The known trick is to
  rewrite the viewport meta `content` (re-assert `initial-scale=1,
  maximum-scale=1`), which snaps Safari back to 1x. Needs testing on iPadOS 26.
  A visible "Reset zoom" control would have to be placed in visual-viewport
  coordinates (`offsetLeft/Top`, scaled by `1/scale`), because `position:
  fixed` follows the layout viewport and would be off-screen too.
- **Absorb.** On a scale change, apply the ratio to the board's zoom and then
  reset the page. Only worth doing if the reset proves reliable.
- **Prevent.** Probably impossible for a trackpad pinch if no cancellable
  event is dispatched. Worth a device test that logs `gesture*`, `wheel` and
  `visualViewport` events during a trackpad pinch before deciding.
- Tests: Chromium cannot produce an iPad trackpad pinch, but
  `Emulation.setPageScaleFactor` can put the page at scale > 1 to test the
  detection and recovery UI. The visual viewport could not be panned in
  headless Chromium (`scrollTo`, wheel and touch scroll all left the offset at
  0), so tests must not depend on that.

## Follow-up: not a trackpad (user report), and what WebKit's source says

The user reports it happens with touch alone, no trackpad. So the trackpad
theory above is wrong for this case. The page-zoom diagnosis from the pixels
still stands. Read against WebKit `main` (raw.githubusercontent.com, Oct 2026):

- **Focus zoom is ruled out on iPad.** `WKContentViewInteraction.mm`
  `_allowScalingToRevealFocusedElement` returns NO unless
  `currentUserInterfaceIdiomIsSmallScreen()`, and the zoom is capped by
  `maximumScaleFactorIgnoringAlwaysScalable` (our `maximum-scale=1`).
- **A page cannot reset a zoom you made yourself.** `WebPage::viewportConfigurationChanged`
  keeps `pageScaleFactor()` once `m_userHasChangedPageScaleFactor` is set, and
  clamps it only to `maximumScale()`. In Safari (`m_forceAlwaysUserScalable`)
  that is `max(meta maximum-scale, 5)`. So rewriting the viewport meta does
  not bring 4x back to 1x. The flag is cleared only by a new page load. The
  "Recover" idea above is withdrawn.
- **The touch defences are best-effort.**
  - `touch-action` is looked up once per finger at touch-down, by hitting the
    topmost compositing view and reading its event region (`touchActionsForPoint`
    in `RemoteLayerTreeViews.mm`). A miss counts as `auto`, which leaves pinch
    and double-tap free for that finger.
  - `scrollViewWillStartPanOrPinchGesture` sets
    `_touchEventsCanPreventNativeGestures = NO`, and so does a touch the page
    has already let through. After that, cancelling `gesturestart` does
    nothing.
  - Which of these leaks here is unknown without the device.

### Solutions offered (none started)

1. **Escape hatch (recommended first).** On `visualViewport` `resize` with
   `scale > 1`, stop cancelling `gesture*`, let the canvas allow `pinch-zoom`,
   and pause the board's own pinch. A pinch-close anywhere then zooms the page
   back out, down to WebKit's minimum of 1. Show a hint pinned to the visual
   viewport. Restore everything at scale 1. It relies only on documented
   behaviour, and can be tested in Chromium with
   `Emulation.setPageScaleFactor`.
2. **Reload fallback.** A "Reset view" button that flushes autosave and
   reloads. It is the only programmatic reset, and it costs undo history.
3. **Find and plug the leak.** An opt-in on-screen diagnostic logging, per
   touch, the target, computed `touch-action`, and whether each `gesture*` was
   cancelable and cancelled, plus `visualViewport.scale`. The user reproduces
   once, then the specific path gets fixed, for example `touch-action: none`
   on non-scrolling chrome so a page pan cannot start there.

## Option 1 built: the way back out of a zoomed page

The user chose option 1. No format change, so no schema, CHANGELOG or version
bump.

### What changed

- **`src/input/pageZoom.ts`**:
  - `isPageZoomed(scale)`, which is `scale > PAGE_ZOOMED_ABOVE` (1.001).
  - `watchPageZoom(viewport, onChange)` reports at once, then on every change.
    It listens to `visualViewport` `resize`.
  - `blockPageZoom` takes an `isPageZoomed` predicate, read at `gesturestart`
    and held for the whole gesture.
  - `PAGE_ZOOMED_CLASS`.
  - The module header now explains why the guards leak and why the page cannot
    reset itself.
- **`src/app/app.ts`**: one `pageZoomed` field drives everything, on touch
  devices only:
  - the class on `<html>`
  - the gesture guard's predicate
  - the controller's `isPageZoomed` option
  - the hint.
- **`src/input/controller.ts`**: new `pagePinch` gesture kind. `beginPinch`
  still abandons the first finger's gesture. On a zoomed page it then sits the
  pinch out instead of zooming the board. Lifting ends it like a pinch, so the
  lift is not recorded as half of a double tap.
- **`src/ui/pageZoomHint.ts`** (new): a `role="status"` note. It is a
  full-width strip that is `position: fixed` at the layout viewport's corner and
  moved onto the visual viewport by `hintPlacement`, which is pure. It is
  repositioned on `resize` and `scroll` while shown.
- **`src/styles/app.css`**:
  - `html.mf-page-zoomed, html.mf-page-zoomed *` get
    `touch-action: pan-x pan-y pinch-zoom`, and the canvas gets `pinch-zoom`.
  - The pill is inverted tokens with a border, so it is visible in dark mode on
    a white board.

### Not verified

- **Not on a real iPad.** This environment has no WebKit. Chromium shows the
  mechanism, and WebKit's source agrees on the parts that matter:
  - `touch-action` includes `pinch-zoom`
  - the gesture events are not cancelled while zoomed
  - `visualViewport` fires `resize` on a zoom.

  It still needs one check on the device.

### Noticed, not changed

- Toasts are `position: fixed` at the layout viewport's bottom, so they are off
  screen while the page is zoomed.
- On a desktop, a trackpad pinch over the top bar zooms the page, and over the
  board it zooms the board, so the way out is a pinch over a part of the chrome
  that is still visible. Out of scope. The mode is touch-only on purpose.
- The leak itself is still unknown. Option 3 (an on-device diagnostic) would
  find it.
- **Pre-existing flaky e2e test, not this change:** `board.spec.ts` › recent
  boards › on startup › "carries the single record of the previous storage
  version forward" fails about 1 run in 20 to 40 with `VersionError: The
  requested version (1) is less than the existing version (2)`. It fails the
  same way on HEAD's build (1 of 40).
  - Cause: the test deletes the `mindflow` IndexedDB and reopens it at
    version 1 while the app is still running. The app's autosave can reopen
    it at version 2 between the delete and the open.
  - Fix idea: seed the legacy database before the app loads, via
    `addInitScript` or a fresh page.
- A full e2e run passed 266 of 266, and a later run 265 of 266, the one
  failure being the flaky test above.
