# 2026-09-24 — Sticky text garbled while editing

On `main`, uncommitted. One bug fix. No format version bump.

## The ask

A long, tab-indented sticky note rendered fine. Once it was double-clicked, or
had a caret in it, every indented line showed as two overlapping, offset copies.
Short notes were fine.

## Root cause

The canvas never hid the text under the editor. The editor's header comment
claimed it did, but no code in the renderer ever did it, back to the initial
commit. Both engines had always drawn the text; it only looked like one copy
while they agreed to the pixel. Three ways they did not, all more likely in a
long note:

1. **Tabs.** The canvas draws one space (HTML text preparation turns ASCII
   whitespace into U+0020). A `<textarea>` advances to the next 8-space tab stop.
   This is what the screenshots show.
2. **Leading spaces.** `wrapText` read an empty `line` as "no word placed yet",
   so `" - x".split(' ')`, which starts with `''`, lost its indent. This only
   happens when wrapping is on, which it is in every sticky.
3. **Overflow.** For text taller than its box, `select()` synchronously scrolls
   the textarea to where the selection ends. For a 20-line note in a 200px
   sticky that was 221px.

## Fix

- `Renderer` has a `displayed` option; `app.ts` points it at
  `TextEditor.displayed`, which blanks the text through `withText(…, '',
  regionKey, { reflow: false })`. A table therefore loses only the edited cell,
  and a content-sized `text` element does not shrink. Only a copy is painted, so
  undo, autosave and the dirty flag are unaffected.
- `whitespaceAsDrawn` in `render/shapes/shared.ts` (`[\t\f\r]` → space, one
  character for one) is step 0 of `wrapText`. The editor applies it on open
  (display only, not written unless the user types), on paste, and in `onInput`
  as a safety net.
- Paste interception uses `execCommand('insertText')` so the textarea's own
  undo still takes the paste back. `setRangeText` is the fallback.
- `wrapText` glues a paragraph's indent onto its first word. Spaces at a soft
  wrap are still swallowed, as in CSS.
- `focusEditor` resets `scrollTop` after `select()` on the mouse path. The touch
  path keeps the scroll because the caret sits at the end for typing.
- The SVG `<text>` now carries `xml:space="preserve"`, or the exporter would
  collapse the spaces the canvas now draws.

## Versioning

No bump. Read literally, the published algorithm ("first word starts the line")
already keeps leading spaces, so the code was out of spec. The tab rule is what
the canvas always did. There is precedent in f42c059, which changed 07-rendering
without a bump.

## Docs

- `docs/07-rendering.md`: wrapping step 0, the step 3 indentation rule, the
  step 4 soft-wrap note, a new "Whitespace" section with an engine table, and
  the HTML-overlay note extended (whitespace, and draw only one copy).
- `ARCHITECTURE.md`: text editing now lists five decisions plus "only one engine
  draws".
- `LEARNINGS.md`: "Never let both engines draw the same text".

## Tests

- Unit: six `wrapText` whitespace cases in `shapes.test.ts`. Five failed before
  the fix; the soft-wrap case passed before and after, as intended.
- E2E: the canvas is ink-free under an open sticky editor; only the edited table
  cell is hidden; an overflowing note does not scroll on open (221 → 0); a tab
  is shown as a space without dirtying the board; a pasted tab becomes a space
  and Cmd+Z undoes the paste. Everything failed on the old build first.
  `inkIn` reads the canvas backing store, which the DOM editor cannot affect.
- 491 unit (was 485), 172 e2e (was 167). Typecheck clean. `index.html` rebuilt.
- Browser pane: the user's note recreated with tabs and overflowing its box.
  Select-all and typing each show one copy at the same position as the normal
  display. After commit the text has no tabs and keeps its one-space indents.

## Noticed, not changed

- CSS breaks after a hyphen (`well-` | `known`, checked in Chromium);
  `wrapText` breaks only at spaces. With one copy drawn this is a reflow on
  open, not doubling. Fixing it means changing the published algorithm or the
  editor's text. Queued as a separate task, and done later the same day (below).
- A `\r\n` file draws a trailing space per line, which shifts centred or
  right-aligned text. This is now documented; the loader does not normalise it.

# 2026-09-24 (later) — Hyphen line breaks (format 1.6.1)

On `main`, uncommitted, on top of 2898561. It was queued as a follow-up from the
fix above.

## The ask and the decision

The textarea breaks after hyphens and the canvas did not, so a hyphenated word
at the wrap edge re-flowed the note when editing started. The options were
(a) teach `wrapText` to break after hyphens, or (b) show U+2011 in the editor.
The user chose **(a)**, **hyphen only** (not `?`), and a **1.6.1 patch** bump.

(b) was weighed seriously. U+2011 is the same width in all four font stacks on
this Mac. It lost on three counts:

- Every typed `-` has to be swapped, so either per-keystroke `execCommand` or a
  lost undo history.
- Copy and cut leak U+2011.
- A genuine U+2011 in a file would be lossily rewritten.

## The rule: Blink's, measured

The task's "after a hyphen that follows a letter" would have been wrong.
Chromium 152 also breaks `2024-` | `09`, `a-` | `-` | `b` and `-` | `foo`. Found by
probing every ASCII pair in a `width: 0` pre-wrap div, where every opportunity
becomes a line. Result:

- Never before `! $ ) , . / : ; ? ] }`.
- Before an ASCII digit only when an ASCII letter or digit precedes the hyphen.
  This is Blink's `ShouldBreakAfter` minus-sign rule.
- Non-ASCII: before a letter (`\p{L}`) unless the hyphen opens its word (ICU
  LB20.1); never before a quote, `…` or a non-ASCII digit.
- A hyphen ending its word is never a break.

Implemented as `breaksAfterHyphen` and `hyphenParts` in `shared.ts`. `wrapText`
now fills over parts, joining a word's first part with `' '` and later parts
with `''`. Char-breaking applies per part.

Safari was not measured. The docs say "expected to agree", because Blink's
tables come from WebKit.

## Fuzz

2,000 random hyphen-heavy strings at random widths against a real textarea:
184 line-count mismatches before, **3 after**, all at 41–45px, where emergency
breaking takes over. With `? « … 中文` added, 30 of 800 mismatch, as expected
with hyphen-only scope.

## Tests

  (height collapsed, `scrollHeight`) with `layoutText`, and checks the canvas

- 503 unit (was 491), 173 e2e (was 172). Typecheck clean. `index.html` rebuilt.

## Found along the way, not changed

- **The reduced-motion reset in `app.css` transitions every property.**
  `transition-duration: 0.01ms !important` on `*` combined with the default
  `transition-property: all` means synchronous layout reads after a style
  change return stale values for users with reduced motion. Nothing listens for
  `transitionend`. Queued as a separate task.
- Remaining browser break points left out on purpose: after `?` before a
  letter, around en and em dashes, before `(`/`[` after closing punctuation,
  and CJK.
