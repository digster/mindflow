# 2026-09-25 — Block page zoom on touch devices

Branch `claude/block-site-zoom-touch-2lqxph`, on top of d9afa91.

## The ask

"Block the site zoom on touch devices, not the board zoom."

## Reproduction

The page already had `user-scalable=no`, and a pinch on the canvas was always
fine because the canvas is `touch-action: none`. Everything else had the
default `auto`. A probe using CDP `Input.dispatchTouchEvent` with a fresh
context per case gave:

| Before | Desktop Chrome + touch | Mobile emulation, meta ignored (like iOS) |
|---|---|---|
| Pinch on the top bar | page 4× | page 5× |
| Pinch on the tool palette | page 4× | page 5× |
| Pinch on the canvas | board 8.5×, page 1× | board 8.5×, page 1× |

Desktop browsers ignore the viewport meta, so the repo's own `touch` project
reproduces the bug as shipped. After the fix, every case leaves the page at 1×,
and the canvas pinch still zooms the board to 8.5×. Chromium would not perform a
double-tap zoom on this page in either mode, so that path is covered by the
spec (any non-`auto` `touch-action` disables it), not by a test.

## Fix: three layers

1. **`touch-action: pan-x pan-y` on `html, body`** in `app.css`. This stops pinch
   and double-tap zoom while panels still scroll. It is repeated on each
   scrolling container: `.mf-style-body`, `.mf-dialog-body`,
   `.mf-recent-list`, `.mf-palette-list`, `.mf-fatal pre`, and `.mf-tools` at
   ≤760px. WebKit resets `touch-action` at scrollers.
2. **`src/input/pageZoom.ts`** has `blockPageZoom(target, touchDevice)`. It
   cancels `gesturestart`, `gesturechange` and `gestureend`, and is the iOS
   Safari backstop. `app.ts` wires it with `navigator.maxTouchPoints > 0`, so
   macOS Safari's trackpad pinch is unchanged. An iPad reports touch points even
   with a trackpad, so it is still covered.
3. **`maximum-scale=1`** in the viewport meta, for the zoom iOS starts by
   itself when a field with small text takes focus.

## Tests

- E2E (`touch.spec.ts` › page zoom, 4 tests): pinching the top bar or the tool
  palette zooms neither the page nor the board; pinching the canvas zooms the
  board and not the page; one finger still scrolls the phone-width palette.
  Mutation runs:
  - The original source fails the two chrome-pinch tests.
  - `touch-action: none` fails the scroll test.
  - `manipulation` fails the pinch tests.
- Unit (`pageZoom.test.ts`, 8 tests):
  - The gesture guard cancels on touch devices, not off them, never touches
    pointer, touch or wheel events, and stops once disposed.
  - The stylesheet: the root rule, every scroller repeating it (removing one
    fails with the selector named), and the canvas kept at `none`.
  - The viewport meta directives.
- 511 unit (was 503). Typecheck clean. `index.html` rebuilt.
- 176 of 177 e2e pass. The one failure is `element clipboard › still pastes when
  the browser fires no native paste event` in the desktop project. It fails the
  same way on the original source in this container, where Chromium 1194 is
  standing in for the pinned 1234 (see 2026-09-22). It is not related to this
  change.

## Docs

- `docs/05-interactions.md` Touch: "The page itself never zooms", with a table
  of the three layers.
- `ARCHITECTURE.md`: an Interaction paragraph, including why the gesture guard
  is the one device-keyed touch rule.
- `README.md` Touch line, and a `CLAUDE.md` "Where things live" row.
- `LEARNINGS.md`: "`user-scalable=no` does not stop the page zooming on a
  touchscreen".
- No format change, so no schema, CHANGELOG or version bump.

## Noticed, not changed

- `docs/05-interactions.md` says browsers report a trackpad pinch as
  `ctrlKey` wheel events. Safari on macOS may send `gesture*` events instead,
  in which case a trackpad pinch there zooms the page rather than the board.
  This was not verified, since there is no Safari here, and desktop is out of
  scope for this change.
- Off the canvas, desktop page zoom (Ctrl + wheel over the top bar, Cmd +/−) is
  still the browser's, on purpose.

# 2026-09-25 (later) — New board in the recent-boards menu

Branch `claude/new-board-dropdown-option-g4h8dh`, on top of b0f2364.

## The ask

"There should also be an option to start a new board along with the recent
boards (within the dropdown)."

## What changed

- `ui/recentBoards.ts`: a **New board** row (`.mf-menu-item.mf-recent-new`,
  Lucide `file-plus` from the existing `ICONS.newBoard`) sits first in the
  popover, then a `.mf-menu-separator`, then the "Recent boards" heading and
  list. New `onNew` option. The row closes the popover and calls `onNew`, the
  same pattern as `onOpen`.
- It is rendered **before** the empty or storage-refused early return, so it
  is always offered. In those states it takes focus, because nothing else can.
- Keyboard: the arrow-key items are now `[newButton, ...openButtons]`, with
  the focus-follows index covering both. Focus still **starts on the first
  reopenable board**, since switching is the main job; New board is one
  ArrowUp or Home away. The existing tests that rely on that start point pass
  unchanged.
- `app/app.ts`: `onNew: () => void this.newBoard()`. `newBoard` already commits
  the text editor, closes popovers and runs `confirmDiscard`, so leaving an
  unsaved board asks exactly as the toolbar button does.
- `app.css`: `.mf-recent-new` packs icon and label to the start (the base menu
  item uses `space-between` for shortcuts), uses the accent colour for the
  icon, and shows the hover background on `:focus-visible` to match a focused
  board row.
- `input/keyboard.ts` shortcut reference: "use the toolbar or the logo menu
  otherwise" for `Cmd/Ctrl + N`.

The logo's accessible name stays "Recent boards". Renaming it was out of scope,
and the e2e suite finds the logo by that name.

## Tests

- E2E, 4 new (`recent boards › New board ×3`, and `…refuses local storage ›
  still offers New board in the menu`). They cover: offered and focused when
  the list is empty, where Enter starts a board with no prompt; cancel keeps
  the board; Continue gives a fresh id and name, a clean board, and the old
  board listed as Unsaved; placed above the first row; ArrowUp, ArrowDown and
  Home reach it; offered when IndexedDB throws. All 4 failed on the old build
  first.
- 511 unit (unchanged). Typecheck clean. `index.html` rebuilt.
- E2E: 180 of 181 pass. The one failure is `element clipboard › still pastes
  when the browser fires no native paste event`. It fails identically with
  `src/` stashed, so it is the known Chromium 1194-vs-1234 issue in this
  container (see the entry above and 2026-09-22). Run through a scratchpad
  config with `NODE_PATH=$PWD/node_modules` so it can resolve
  `@playwright/test`.
- Browser check: screenshots in light and dark mode, with the list empty and
  with two boards, including the keyboard-focus ring on New board. Screenshots
  deleted afterwards.

## Docs

- `docs/05-interactions.md` Recent boards: a New board bullet, and the
  keyboard bullet now covers New board and where focus starts.
- `docs/06-persistence.md`: one sentence saying the menu also starts a board.
- `README.md` Recent boards line.
- `LEARNINGS.md`: the menu opens asynchronously, so a key pressed straight
  after the click goes to the board.
- No format change, so no schema, CHANGELOG or version bump.
